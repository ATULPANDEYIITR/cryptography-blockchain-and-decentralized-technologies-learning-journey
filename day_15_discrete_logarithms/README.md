# Discrete logarithms

## Topic introduction

A discrete logarithm is the inverse problem of modular exponentiation.

For a group element `g` and target `h`, the basic problem is to find an exponent `x` satisfying

`g^x ≡ h (mod p)`.

The operation of computing `g^x mod p` is normally straightforward, even when `x` is large. The reverse operation, recovering `x` from `g`, `h`, and the modulus, can be substantially harder when the group and its parameters are selected appropriately.

This asymmetry is one of the foundations of several public-key cryptographic systems and protocols. Discrete logarithms are closely related to Diffie-Hellman key exchange, ElGamal encryption, digital-signature constructions, finite-field cryptography, and elliptic-curve cryptography.

The three implementations approach the subject from different directions:

- Python provides a complete mathematical study with modular arithmetic, discrete-log algorithms, group analysis, Diffie-Hellman, ElGamal, edge cases, and tests.
- JavaScript emphasizes exact `BigInt` arithmetic, reusable functions, application-friendly execution, and implementation behavior specific to JavaScript.
- C++ develops an industry-style case study around a deliberately weak key-exchange domain, including domain validation, algorithm selection, attack simulation, performance measurement, and modular design.

All numerical parameters are intentionally small. They make the algorithms observable and executable but are not cryptographically secure.

## Fundamental concepts

### Modular arithmetic

For integers `a` and positive modulus `m`, the expression

`a mod m`

denotes the remainder after division by `m`.

Congruence is written as

`a ≡ b (mod m)`

when `m` divides `a - b`.

For example,

`17 ≡ 5 (mod 12)`

because `17 - 5 = 12`.

Modular arithmetic allows addition and multiplication to be performed while keeping values inside a finite residue system.

### Modular exponentiation

Modular exponentiation computes

`g^x mod p`

without first constructing the potentially enormous integer `g^x`.

The standard method is repeated squaring. If the exponent is represented in binary, each bit determines whether the current power contributes to the result.

The implementations call this operation `mod_pow`, `modPow`, or `modular_power`.

Its basic complexity is logarithmic in the exponent when measured by the number of modular multiplications.

### Modular inverse

A number `a` has an inverse modulo `m` when there exists `a^-1` such that

`a × a^-1 ≡ 1 (mod m)`.

Such an inverse exists exactly when

`gcd(a, m) = 1`.

The extended Euclidean algorithm computes the inverse efficiently.

The implementations use this operation throughout discrete-log algorithms, particularly when rearranging modular equations.

### Multiplicative groups

For a prime `p`, the nonzero residues

`1, 2, ..., p - 1`

form a multiplicative group modulo `p`, commonly written as `F_p*`.

This group contains `p - 1` elements.

The group operation is multiplication modulo `p`.

Every nonzero element has a modular inverse.

### Subgroups

A base `g` does not necessarily generate the entire multiplicative group.

The subgroup generated by `g` is written

`<g> = {g^0, g^1, g^2, ...}`.

The number of distinct elements in this subgroup is the multiplicative order of `g`.

If `ord(g) = n`, then

`g^n ≡ 1 (mod p)`,

and exponent values repeat modulo `n`.

This distinction is important. If `g` does not generate the complete group, a discrete logarithm is unique only modulo `ord(g)`.

### Multiplicative order

The order of `g` modulo `p` is the smallest positive integer `n` satisfying

`g^n ≡ 1 (mod p)`.

For a prime modulus, the order divides `p - 1`.

If the order equals `p - 1`, `g` is a generator, also called a primitive root of the multiplicative group.

The Python and C++ implementations explicitly calculate the order for educational purposes.

## The discrete logarithm problem

The discrete logarithm problem asks:

Given `g`, `h`, and a group, find `x` such that

`g^x = h`.

In a finite field this is commonly expressed as

`g^x ≡ h (mod p)`.

The corresponding exponent `x` is a discrete logarithm of `h` to the base `g`.

The notation

`x = log_g(h)`

is useful conceptually, but it should not be interpreted as an ordinary real-valued logarithm.

There are several important differences between ordinary and discrete logarithms.

Ordinary logarithms operate over a continuous numerical domain and can be evaluated using analytical functions.

Discrete logarithms operate in a finite algebraic structure. Exponents are periodic, and a solution exists only when the target belongs to the subgroup generated by the base.

## Solvability

A discrete logarithm exists for `g` and `h` only when `h` belongs to `<g>`.

If `ord(g) = n`, then the possible powers are

`g^0, g^1, ..., g^(n-1)`.

After that point the sequence repeats.

The Python implementation explicitly constructs the generated subgroup and tests targets that are both inside and outside it.

This is an important distinction from the simplified statement that every nonzero `h` automatically has a logarithm.

## Uniqueness and exponent classes

Suppose

`ord(g) = n`.

If `g^x = h`, then every exponent

`x + kn`

for an integer `k` produces the same group element.

Therefore discrete logarithms are naturally considered modulo the order of the base.

For a generator of the entire multiplicative group modulo a prime `p`, the exponent is normally considered modulo `p - 1`.

For a non-generator, the relevant modulus is smaller.

## Brute-force discrete logarithms

The simplest algorithm is exhaustive search.

Start with

`g^0 = 1`.

Then calculate

`g^1`, `g^2`, `g^3`, and so on until the target is found.

The Python function `brute_force_discrete_log`, the JavaScript function `bruteForceDiscreteLog`, and the C++ function `brute_force_discrete_log` implement this method.

Its advantages are simplicity, predictable behavior, and constant additional memory.

Its main disadvantage is time.

If the group has order `n`, exhaustive search can require approximately `n` group operations.

This becomes impractical rapidly as the group grows.

## Baby-step giant-step

Baby-step giant-step is a classic time-memory trade-off.

Suppose the order of the group is `n`.

Choose

`m = ceil(sqrt(n))`.

Write the unknown exponent as

`x = im + j`.

The discrete-log equation becomes

`g^(im+j) = h`.

Rearranging gives

`g^j = h × g^(-im)`.

The algorithm therefore separates the search into two components.

The baby steps store values

`g^j`

for a range of `j`.

The giant steps repeatedly multiply by

`g^(-m)` and search for a collision with the stored baby steps.

When a collision is found, `i` and `j` reconstruct `x`.

The implementations use a hash table or map to store the baby steps.

### Complexity

For group order `n`:

- Time: approximately `O(sqrt(n))`
- Memory: approximately `O(sqrt(n))`

This is a major improvement over exhaustive search but requires substantially more memory.

The C++ implementation uses `std::unordered_map`, while the JavaScript implementation uses `Map`.

## Pollard's rho for discrete logarithms

Pollard's rho is another generic discrete-log algorithm.

Unlike baby-step giant-step, it does not require a table containing approximately `sqrt(n)` group elements.

A state is represented in the form

`g^alpha h^beta`.

A pseudorandom walk repeatedly transforms the state.

When two states collide, the equality between their representations produces an equation involving the unknown discrete logarithm.

The Python, JavaScript, and C++ implementations maintain `value`, `alpha`, and `beta` state variables.

### Complexity

The expected generic-group running time is approximately

`O(sqrt(n))`.

Its principal memory advantage is that only a small amount of state is needed.

The trade-off is more complicated control flow and probabilistic behavior. A collision can sometimes produce an unusable modular equation, requiring another walk.

## Pohlig-Hellman

Pohlig-Hellman exploits the factorization of the group order.

Suppose the order is

`n = q1^e1 q2^e2 ... qk^ek`.

Instead of solving the entire discrete-log problem directly, the algorithm reduces it to discrete logarithms in subgroups associated with the prime-power factors.

The resulting congruences are combined using the Chinese remainder theorem.

This means that the difficulty of a discrete logarithm depends not only on the numerical size of the group but also on the factorization of its order.

A group whose order contains only small prime factors is particularly unsuitable for applications that depend on discrete-log hardness.

The Python, JavaScript, and C++ implementations use educational versions of Pohlig-Hellman. Their prime-order subproblems are solved by direct search so that the reduction is easy to inspect.

Production implementations use substantially more optimized algorithms.

## Chinese remainder theorem

The Chinese remainder theorem combines congruences such as

`x ≡ a1 (mod n1)`

and

`x ≡ a2 (mod n2)`

when the moduli are pairwise coprime.

The result determines `x` modulo

`n1 × n2`.

Pohlig-Hellman relies on this reconstruction step to combine discrete-log results obtained in smaller subgroups.

All three implementations contain a CRT routine.

## Comparison of the main algorithms

| Algorithm | Typical time | Memory | Main property |
|---|---:|---:|---|
| Brute force | `O(n)` | `O(1)` | Simplest method |
| Baby-step giant-step | `O(sqrt(n))` | `O(sqrt(n))` | Time-memory trade-off |
| Pollard rho | `O(sqrt(n))` expected | `O(1)` | Generic low-memory method |
| Pohlig-Hellman | Depends on factorization | Depends on implementation | Exploits smooth group order |

No single algorithm is universally best.

Baby-step giant-step is attractive when memory is available.

Pollard rho is attractive when memory is constrained.

Pohlig-Hellman is especially important when the group order has small prime factors.

Brute force is useful for teaching, testing, and tiny groups.

Discrete logarithms require exact integer operations, so ordinary floating-point `Number` arithmetic is inappropriate for large integer values.

The JavaScript implementation therefore represents mathematical integers with values such as `29n`.

### BigInt arithmetic

The JavaScript file implements:

For example, `9007199254740993n` is an exact `BigInt`, while ordinary JavaScript `Number` uses IEEE-754 floating-point representation and cannot exactly represent every integer beyond the safe-integer range.

### JavaScript BSGS

## C++ case study

The C++ implementation models a small key-exchange service operating in a finite multiplicative group.

The service has a public domain:

`(p, g)`

where `p` is the modulus and `g` is the generator or group element.

A participant selects a private exponent `x` and publishes

`g^x mod p`.

Another participant performs the same process.

### Domain model

The `KeyExchangeDomain` class encapsulates:

- modulus
- generator
- public-value generation
- shared-value calculation

The constructor validates that the generator is invertible.

This demonstrates an important design principle: invalid mathematical state should be rejected at the boundary of a component rather than allowed to propagate through the application.

### Shared-secret mechanism

Alice computes

`A = g^a mod p`.

Bob computes

`B = g^b mod p`.

Alice then calculates

`B^a = g^(ab) mod p`.

Bob calculates

`A^b = g^(ab) mod p`.

Both obtain the same mathematical value.

The implementation demonstrates this process directly.

### Attack simulation

The deliberately weak modulus allows the `DiscreteLogAuditService` to recover a private exponent from an observed public value using baby-step giant-step.

The service then verifies the recovered exponent by recomputing

`g^x mod p`.

This is an important engineering property.

An algorithm should not be considered successful merely because it returns a candidate. The candidate should be independently verified against the original equation.

### Performance measurement

The C++ case study uses `std::chrono::steady_clock` to measure execution time.

It compares:

- exhaustive search
- baby-step giant-step
- Pollard rho

The measurements are useful for illustrating scaling trends but should not be interpreted as cryptographic benchmarks.

Compiler optimization level, hardware, memory hierarchy, implementation details, and parameter sizes all influence actual performance.

### Arithmetic implementation

The C++ program uses `unsigned __int128` internally for multiplication of 64-bit operands before reduction.

This helps prevent intermediate multiplication overflow for the small educational parameters.

This is still not a general arbitrary-precision cryptographic implementation.

Cryptographic-scale parameters normally require carefully designed big-integer arithmetic and constant-time considerations.

## Diffie-Hellman and discrete logarithms

Diffie-Hellman uses exponentiation in a group.

The public values are

`A = g^a`

and

`B = g^b`.

The shared value is

`g^(ab)`.

An observer can see `g`, `A`, and `B`, but recovering `a` from `A` requires solving a discrete logarithm.

This illustrates why the discrete logarithm problem is important to cryptographic protocol design.

The relationship should not be oversimplified into the claim that breaking Diffie-Hellman is always exactly equivalent to solving one ordinary discrete logarithm. Different computational assumptions are involved, including the computational Diffie-Hellman problem and the decisional Diffie-Hellman problem.

## ElGamal

ElGamal encryption uses similar group structure.

The private key is an exponent `x`.

The public key contains

`y = g^x`.

For an ephemeral exponent `k`, encryption creates a pair containing a group element derived from `g^k` and a message masked by a shared group value.

Decryption uses the private exponent to recreate that shared value and remove the mask.

The Python and JavaScript implementations demonstrate this algebra using small finite fields.

Modern production systems require carefully specified variants, secure randomness, authenticated encryption where appropriate, parameter validation, and audited cryptographic implementations.

## Edge cases

### Target outside the generated subgroup

If `h` is not in `<g>`, no discrete logarithm exists for that base and target.

A correct implementation should return failure rather than inventing an exponent.

### Base without an inverse

If

`gcd(g, p) != 1`,

then `g` is not an element of the multiplicative group modulo `p`.

Modular inverse operations involving such a value may fail.

### Non-generator bases

When `g` has order smaller than `p - 1`, exponent values repeat according to `ord(g)` rather than `p - 1`.

Algorithms must use the correct group order.

### Multiple solutions

A discrete logarithm can have infinitely many integer representatives because

`g^(x + kn) = g^x`

when `n = ord(g)`.

The meaningful result is therefore an exponent class modulo the group order.

### Pollard-rho collisions

Not every collision immediately produces an invertible equation.

The denominator obtained from a collision may not be invertible modulo the group order.

A robust implementation must detect such cases and retry rather than treating the collision as automatically successful.

## Common mistakes

### Treating discrete logarithms like ordinary logarithms

The expression `log_g(h)` in a finite group is not evaluated using ordinary logarithm functions.

The problem is defined through group operations.

### Ignoring the group order

Using `p - 1` without checking the order of `g` can produce incorrect results for non-generators.

### Forgetting subgroup membership

A target outside the generated subgroup has no solution.

### Using floating-point integers

JavaScript `Number` values are not suitable for arbitrary large exact integer arithmetic.

The JavaScript implementation uses `BigInt`.

### Assuming small demonstrations are secure

A modulus such as `29`, `101`, `1009`, or `10007` is trivially unsuitable for cryptographic protection.

The examples are intentionally weak so that algorithms can finish quickly.

### Assuming one algorithm dominates every case

BSGS, Pollard rho, and Pohlig-Hellman have different resource profiles.

Algorithm choice depends on group structure, available memory, expected workload, and parameter properties.

### Failing to verify an answer

After finding a candidate `x`, calculate

`g^x mod p`

and compare it with the target.

This simple verification catches implementation errors and invalid candidate reconstruction.

## Advanced concepts

### Generic-group complexity

For a generic group of order `n`, the best-known basic attacks commonly discussed in this context have square-root-scale complexity.

BSGS requires roughly square-root time and square-root memory.

Pollard rho requires roughly square-root expected time with very small memory.

This square-root behavior is the reason cryptographic groups need substantially larger parameters than would be suggested by a naive comparison with the group order itself.

### Smooth versus non-smooth group orders

Pohlig-Hellman shows why the factorization of the group order is fundamental.

If the order factors into small prime powers, the discrete logarithm can be reduced to easier subproblems.

A secure group therefore cannot be selected solely by looking at the size of its modulus.

The structure of the group order matters.

### Time-memory trade-offs

BSGS stores a large table to reduce computation.

Pollard rho sacrifices predictable memory usage in exchange for a probabilistic walk.

This is a general algorithmic design pattern:

- more memory can reduce computation
- less memory can require additional computation
- specialized mathematical structure can reduce both

### Finite fields versus elliptic curves

The implementations in this study use multiplicative groups modulo integers, particularly finite fields.

Elliptic-curve cryptography uses a different group operation defined by points on an elliptic curve.

The discrete-log problem still exists in the elliptic-curve setting, but the group elements and arithmetic are different.

The relevant algorithms and security parameters therefore differ.

The conceptual pattern remains:

`easy group operation`

versus

`hard inverse problem`.

## Security considerations

The mathematical hardness of discrete logarithms is useful only when the complete cryptographic system is designed correctly.

Important considerations include:

- appropriate standardized groups
- sufficiently large security parameters
- subgroup validation
- secure generation of private exponents
- cryptographically secure randomness
- protection against side-channel attacks
- constant-time implementations where required
- careful public-key validation
- avoidance of custom cryptographic protocols
- authenticated communication when confidentiality and integrity are required
- secure key derivation rather than directly treating arbitrary group elements as application keys

The small parameters in these implementations intentionally violate cryptographic security requirements.

The code should therefore be viewed as an algorithmic laboratory, not as a secure cryptographic implementation.

## Performance considerations

The dominant scaling parameter is the group order.

For exhaustive search, doubling the order can approximately double the search space.

For BSGS and Pollard rho, the characteristic generic complexity grows approximately with the square root of the order.

Memory is a major differentiator.

BSGS needs storage for approximately `sqrt(n)` group elements.

Pollard rho needs only a small amount of state but performs a probabilistic search.

Pohlig-Hellman can be dramatically faster than generic methods when the group order factors into small prime powers.

The implementations measure runtime for small examples to make these differences observable.

Such measurements should not be extrapolated directly to cryptographic parameters.

## Important distinctions

### Modular exponentiation versus discrete logarithm

Modular exponentiation:

`given g and x, compute g^x mod p`

is generally efficient.

Discrete logarithm:

`given g and h, recover x from g^x = h`

is designed to be difficult in suitable cryptographic groups.

### Group size versus group order

The modulus determines the surrounding arithmetic structure, while the order of the particular element determines the exponent cycle relevant to a discrete logarithm.

Confusing these quantities can lead to incorrect algorithm implementations.

### BSGS versus Pollard rho

BSGS provides a predictable square-root search with substantial memory consumption.

Pollard rho uses very little memory but has probabilistic runtime and collision handling requirements.

### Generic attacks versus structure-aware attacks

BSGS and Pollard rho are generic algorithms that do not exploit much special structure.

Pohlig-Hellman explicitly exploits the factorization of the group order.

This distinction is central to understanding why cryptographic parameter selection considers algebraic structure rather than only numerical size.

## Testing strategy

The three implementations include deterministic tests for:

- modular exponentiation
- discrete-log recovery
- candidate verification
- CRT reconstruction
- invalid modular inverses
- subgroup-related failures
- key-exchange consistency

Testing a discrete-log implementation should always include both positive and negative cases.

A positive case verifies that a known exponent can be recovered.

A negative case verifies that an implementation correctly reports that no discrete logarithm exists.

Independent verification with modular exponentiation is particularly important because the original equation is simple to evaluate even when its inverse is difficult.

## Production considerations

The implementations intentionally use educational algorithms and small parameters.

A production cryptographic implementation should not substitute custom versions of these routines for standardized, audited cryptographic libraries.

Important production concerns include exact parameter selection, secure randomness, side-channel resistance, constant-time behavior where necessary, subgroup validation, error handling, memory management, secure key storage, protocol authentication, and independent security review.

The mathematical algorithms remain valuable even when production software delegates the low-level cryptography to specialized libraries. Understanding the underlying discrete-log problem makes it possible to reason about what those libraries are designed to protect and why parameter selection matters.
