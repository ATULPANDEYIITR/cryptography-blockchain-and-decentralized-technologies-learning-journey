# MAC in Cryptography and Blockchain

## 1. Introduction

A Message Authentication Code (MAC) is a cryptographic mechanism used to verify the integrity and authenticity of a message using a shared secret key.

A MAC allows a sender and receiver who possess the same secret key to determine whether a message has been modified and whether its authentication tag was generated by someone possessing that key.

MAC mechanisms are relevant to:

- Secure communication between distributed systems.
- Blockchain transaction processing.
- Peer-to-peer network authentication.
- Consensus message validation.
- API request authentication.
- Payment processing.
- Distributed database replication.
- Integrity protection for stored records.

The implementations use HMAC-SHA256 as their primary authentication mechanism.

## 2. Cryptographic Foundations

### 2.1 Message Authentication Code

A MAC is generated from two inputs:

1. A secret cryptographic key.
2. A message requiring authentication.

The resulting authentication tag is verified by another party possessing the same key.

The fundamental operation is:

\[
T = MAC(K,M)
\]

Where:

- \(T\) = authentication tag.
- \(K\) = shared secret key.
- \(M\) = message.

The receiving party independently calculates:

\[
T' = MAC(K,M)
\]

Authentication succeeds when the independently calculated tag matches the supplied tag.

\[
T'=T
\]

A mismatch indicates that the message, key, or authentication data is incorrect.

A MAC does not encrypt the message. Confidentiality requires a separate encryption mechanism.

### 2.2 HMAC

HMAC is a standardized construction that combines a cryptographic hash function with a secret key.

For HMAC-SHA256:

\[
HMAC(K,M)=
H((K'\oplus opad)\parallel
H((K'\oplus ipad)\parallel M))
\]

Where:

- \(H\) = SHA-256.
- \(K'\) = normalized key.
- \(M\) = message.
- \(ipad\) = inner padding.
- \(opad\) = outer padding.
- \(\oplus\) = XOR.
- \(\parallel\) = concatenation.

SHA-256 produces a 256-bit digest.

Consequently, HMAC-SHA256 produces a 32-byte authentication tag.

The construction uses separate inner and outer hashing operations. It is not equivalent to simply calculating `SHA256(secret || message)`.

### 2.3 MAC and Digital Signatures

MACs and digital signatures provide different authentication models.

| Property | MAC | Digital signature |
|---|---|---|
| Key model | Shared secret | Private and public key pair |
| Generation | Shared secret | Private key |
| Verification | Shared secret | Public key |
| Public verification | No | Yes |
| Non-repudiation | No | Supports public attribution |
| Typical use | Internal authentication | Public transaction authorization |
| Key distribution | Secret sharing | Public-key distribution |

A participant possessing a shared MAC key can generate valid authentication tags. Therefore, another participant holding the same key cannot independently prove which participant generated a particular tag.

This distinction is particularly important in public blockchains.

Public blockchain transactions generally use digital signatures rather than HMAC because independent network participants must verify transaction authorization without sharing the transaction creator's private secret.

## 3. MAC Algorithms

Different MAC constructions address different cryptographic requirements.

| Algorithm | Construction | Characteristics |
|---|---|---|
| HMAC-SHA256 | Hash-based | Widely applicable and standardized |
| HMAC-SHA512 | Hash-based | Uses SHA-512 |
| CMAC-AES | Block-cipher-based | Uses AES |
| GMAC | Authenticated-encryption-based | Authentication mechanism associated with GCM |
| Poly1305 | Universal-hash-based | Commonly paired with ChaCha20 |

The implementations in this project focus on HMAC-SHA256.

### HMAC versus ordinary hashing

A cryptographic hash function calculates:

\[
H(M)
\]

Anyone possessing the message can independently calculate the same digest.

HMAC calculates:

\[
HMAC(K,M)
\]

An attacker who does not possess the secret key should not be able to generate a valid authentication tag for a modified message, assuming a secure implementation and key.

## 4. Message Authentication Workflow

A typical authenticated communication workflow is:

1. The sender constructs a message.
2. The sender selects an authorized secret key.
3. The message is serialized deterministically.
4. HMAC-SHA256 generates the authentication tag.
5. The message and tag are transmitted.
6. The receiver identifies the appropriate key.
7. The receiver independently calculates the expected tag.
8. The receiver compares the tags.
9. The receiver accepts or rejects the message.

Plain-text representation:

    Original Message
          |
          v
    Canonical Serialization
          |
          v
    Secret Key + Message
          |
          v
       HMAC-SHA256
          |
          v
    Authentication Tag
          |
          v
    Message Transmission
          |
          v
    Receiver Recalculates MAC
          |
          v
    Constant-Time Comparison
          |
          +------ Match ------> Accept
          |
          +------ Mismatch ---> Reject

### 4.1 Canonical Serialization

Two systems must authenticate exactly the same message bytes.

Consider:

- `{"amount":100,"sender":"A"}`
- `{"sender":"A","amount":100}`

These JSON documents represent equivalent data, but their byte sequences differ.

Calculating a MAC directly over differently serialized messages produces different authentication tags.

Canonical serialization provides a deterministic representation.

The implementations use sorted keys and controlled serialization rules.

For production protocols, the serialization format must also define:

- Character encoding.
- Numeric representation.
- Unicode normalization.
- Null handling.
- Array ordering.
- Field inclusion.
- Version compatibility.

Ambiguous serialization can invalidate an otherwise correct cryptographic protocol.

## 5. Key Management

The security of HMAC depends heavily on the secrecy and management of its key.

The project implements a key registry with:

- Unique key identifiers.
- Secret-key validation.
- Key retrieval.
- Algorithm identification.
- Duplicate-key rejection.
- Key lifecycle metadata.

### Key generation

Cryptographic keys must be generated using a cryptographically secure random number generator.

The implementations use:

| Language | Random generation |
|---|---|
| Python | `secrets.token_bytes()` |
| JavaScript | `crypto.randomBytes()` |
| C++ | Supplied demonstration key |
| Java | `SecureRandom` |
| PostgreSQL | Demonstration key records |

A 256-bit key is used for HMAC-SHA256 demonstrations.

Key length alone does not guarantee security. Key generation, storage, access control, rotation, and revocation are equally important.

### Key rotation

A production key lifecycle should include:

    Key Generation
          |
          v
    Key Registration
          |
          v
    Active Authentication
          |
          v
    New Key Introduction
          |
          v
    Old Key Retirement
          |

Key rotation requires a controlled transition because messages or transactions authenticated using an old key may still require verification.

Key identifiers allow the receiver to select the appropriate key without transmitting the secret itself.

## 6. Constant-Time Verification

Ordinary string comparison can stop at the first differing character.

In some environments, this behavior can reveal information about how much of an authentication tag matches the expected value.

A constant-time comparison is designed to avoid revealing the matching prefix through ordinary early-exit behavior.

The implementations use:

| Language | Mechanism |
|---|---|
| Python | `hmac.compare_digest()` |
| JavaScript | `crypto.timingSafeEqual()` |
| C++17 | Fixed-length XOR accumulation |
| Java 17 | `MessageDigest.isEqual()` |
| PostgreSQL | Demonstration byte comparison |

The C++ implementation accumulates differences across the complete 32-byte tag.

The JavaScript implementation first verifies that both buffers have equal lengths because `timingSafeEqual()` requires equal-length inputs.

Constant-time comparison is one security control, not a complete defense against every timing, memory, compiler, or side-channel attack.

## 7. MAC in Blockchain Systems

Blockchain systems combine cryptographic hashing, transaction authorization, distributed validation, and consensus.

MAC mechanisms can be used in permissioned blockchain environments where participating organizations or nodes share controlled authentication secrets.

Typical applications include:

- Authentication between validator nodes.
- Private consortium network communication.
- Authenticated internal transaction relaying.
- Protected consensus messages.
- Inter-service communication.
- Permissioned data exchange.

### 7.1 Transaction Authentication

A blockchain transaction contains structured information such as:

- Transaction identifier.
- Sender.
- Receiver.
- Amount.
- Nonce.
- Key identifier.
- Authentication tag.

The transaction MAC covers the transaction's canonical representation.

If any authenticated field changes, the calculated MAC should no longer match.

For example:

| Field | Original | Modified |
|---|---|---|
| Sender | Wallet A | Wallet A |
| Receiver | Wallet B | Wallet B |
| Amount | 100 | 900 |
| Nonce | 1 | 1 |
| MAC | Original tag | Invalid for modified data |

The authentication service rejects the modified transaction.

### 7.2 Blockchain Hash Linking

A blockchain block contains a reference to the preceding block.

A simplified structure is:

    Block 0
       |
       v
    Block 1
       |
       v
    Block 2
       |
       v
    Block 3

Each block contains:

- Block index.
- Timestamp.
- Previous block hash.
- Transaction collection.
- Current block hash.

A simplified block hash is:

\[
H_i=SHA256(B_i)
\]

Where \(B_i\) is the canonical block representation.

A change to an earlier block changes its hash and causes a mismatch with the next block's stored previous hash.

### 7.3 MAC and Blockchain Hashing Are Different

These mechanisms must not be confused.

| Mechanism | Main purpose | Secret required |
|---|---|---|
| SHA-256 | Cryptographic hashing | No |
| HMAC-SHA256 | Message authentication | Yes |
| Block hash | Block integrity reference | No |
| Digital signature | Transaction authorization | Private key |
| Consensus | Agreement on accepted blockchain state | Protocol-dependent |

A block hash does not prove that a transaction was authorized.

A valid transaction MAC does not establish consensus among blockchain participants.

A blockchain hash chain does not independently provide confidentiality.

A complete blockchain architecture requires these mechanisms to operate together under appropriate rules.

## 8. Replay Protection

A replay attack occurs when an attacker captures a previously authenticated message and submits it again.

The authentication tag may still be valid because the original message has not changed.

Therefore, MAC verification alone does not prevent replay attacks.

The project introduces nonces.

A nonce is a value intended to distinguish one authenticated operation from another.

A message can include:

- Sender identifier.
- Message identifier.
- Nonce.
- Timestamp.
- Key identifier.
- Payload.
- MAC.

The receiver checks:

1. Whether the MAC is valid.
2. Whether the timestamp falls within the accepted time window.
3. Whether the nonce has already been processed.
4. Whether the sender is authorized.

The replay-protection rule is:

\[
(sender,nonce)\notin ProcessedNonces
\]

After successful processing, the nonce is recorded.

For distributed production systems, nonce validation and transaction processing must be atomic. Otherwise, two concurrent requests may both pass a check before either records the nonce.

Persistent storage and database uniqueness constraints provide stronger replay protection than an in-memory set.

## 11. C++17 Implementation

The C++ implementation provides a lower-level cryptographic perspective.

It includes an educational implementation of SHA-256 and HMAC-SHA256 without external libraries.

### SHA-256 implementation

The SHA-256 class performs:

1. Message padding.
2. Message-length encoding.
3. Block processing.
4. Message schedule expansion.
5. Compression rounds.
6. Digest construction.

SHA-256 processes 512-bit message blocks and maintains eight 32-bit state words.

The compression function uses:

- Bitwise rotations.
- XOR.
- Choice.
- Majority.
- Modular 32-bit addition.

The implementation checks the standard SHA-256 empty-input test vector.

### HMAC implementation

The HMAC class:

1. Normalizes the key.
2. Applies the inner padding.
3. Hashes the inner message.
4. Applies the outer padding.
5. Calculates the final SHA-256 digest.

The implementation demonstrates how a hash-based MAC is constructed rather than relying on a third-party cryptographic library.

### Blockchain governance

The C++ blockchain engine includes:

- Transaction validation.
- Key registry lookup.
- MAC verification.
- Duplicate transaction detection.
- Block creation.
- Previous-hash validation.
- Transaction integrity checks.

Integer minor currency units are used instead of floating-point amounts to avoid monetary precision errors.

The handwritten cryptographic implementation is intended for learning and testing. Production cryptographic systems should use maintained, independently audited cryptographic libraries.

The SQL verification function uses PostgreSQL byte comparison. It does not claim a constant-time comparison guarantee. A production authentication boundary should use a suitable audited verification implementation.

## 14. MAC Security Properties

A secure MAC implementation should address the following properties.

### Integrity

A modified message should not pass authentication.

### Authentication

A valid tag demonstrates that the message was authenticated by an entity possessing the shared secret, subject to the security of the algorithm and key.

### Unforgeability

An attacker without the secret key should not be able to generate a valid authentication tag for a new message except with negligible probability.

### Replay resistance

A valid old message should not be accepted repeatedly when the protocol requires unique operations.

### Key isolation

A compromised key should not automatically compromise unrelated communication domains.

Separate keys should be used for different security boundaries and purposes.

## 15. Security Threats and Failure Conditions

| Threat | Description | Control |
|---|---|---|
| Message modification | Unauthorized changes to authenticated content | HMAC verification |
| Key disclosure | Attacker obtains the secret key | KMS/HSM and access controls |
| Replay attack | Previously valid message is resubmitted | Nonces and persistent replay tracking |
| Weak key generation | Predictable authentication keys | Cryptographically secure randomness |
| Serialization mismatch | Sender and receiver authenticate different bytes | Canonical serialization |
| Timing leakage | Tag comparison reveals information | Constant-time comparison |
| Key expiration | Authentication uses an expired key | Key lifecycle validation |
| Duplicate transaction | Same transaction is committed more than once | Unique constraints |
| Unauthorized key use | Unapproved node uses a shared key | Key-to-node authorization |
| Block modification | Stored block data changes | Recalculated block hashes |
| Concurrent replay | Multiple requests use the same nonce | Atomic database operations |

## 16. MAC Limitations in Blockchain

MACs are not a replacement for the cryptographic mechanisms used by public blockchains.

A permissionless blockchain requires transaction authorization that can be verified by independent participants.

HMAC requires possession of the shared secret.

If every validator shares a single HMAC key, every validator can generate authentication tags. Consequently, HMAC alone cannot establish which individual validator or transaction creator authorized a particular operation.

Public-key digital signatures solve a different problem.

For public blockchain transaction authorization, systems commonly use asymmetric cryptography.

For permissioned blockchain communication, MACs can provide efficient authentication between trusted nodes.

A practical architecture can therefore combine:

- Digital signatures for transaction authorization.
- HMAC for authenticated internal communication.
- SHA-256 or other approved hash functions for integrity references.
- Consensus protocols for distributed agreement.
- Encryption for confidentiality.
- Nonce management for replay resistance.

These mechanisms serve separate purposes and should be designed as complementary security controls.

## 17. Performance and Complexity

Let:

- \(n\) = message length in bytes.
- \(b\) = number of SHA-256 blocks processed.
- \(t\) = number of transactions in a block.
- \(c\) = number of blocks in a blockchain.

| Operation | Expected complexity |
|---|---|
| SHA-256 | \(O(n)\) |
| HMAC-SHA256 | \(O(n)\) |
| MAC verification | \(O(n)\) |
| Key lookup using hash map | Average \(O(1)\) |
| Nonce lookup using hash set | Average \(O(1)\) |
| Block transaction validation | \(O(t \cdot n)\) for total serialized transaction size |
| Full blockchain validation | Proportional to total stored block and transaction data |

The implementations use in-memory collections for educational clarity.

The C++ blockchain duplicate-transaction search scans existing blocks, which can become expensive as the chain grows.

A production implementation should use indexed transaction identifiers and persistent state.

The PostgreSQL implementation creates indexes for frequently queried relationships and transaction states.

## 18. Practical Applications

MAC mechanisms are useful in systems where two or more trusted components share an authentication secret.

Examples include:

- Authentication between permissioned blockchain nodes.
- Internal financial-service communication.
- Distributed ledger replication.
- Secure API request authentication.
- Enterprise transaction gateways.
- Message integrity in IoT systems.
- Protected inter-service communication.
- Authenticated distributed consensus messages.

The appropriate choice depends on the trust model, key-distribution architecture, authentication requirements, and whether independent public verification is necessary.

## 21. Technical Limitations

The implementations intentionally model a simplified blockchain environment.

They do not implement:

- Distributed consensus.
- Mining or proof of work.
- Proof of stake.
- Merkle trees.
- Public-key wallet authorization.
- Production-grade key custody.
- Distributed transaction finality.
- Network-wide validator synchronization.
- Byzantine fault tolerance.
- Confidential transaction protocols.
- Hardware-backed cryptographic operations.

The C++ implementation provides educational SHA-256 and HMAC code rather than an independently audited cryptographic implementation.

The Python, JavaScript, and Java implementations rely on their standard cryptographic libraries.

The PostgreSQL implementation uses demonstration key storage and does not guarantee constant-time MAC comparison.

The blockchain models use simplified block serialization and should not be interpreted as complete production blockchain protocols.

## 22. Final Technical Distinction

The central architectural distinction is between authentication, integrity, authorization, and consensus.

| Security mechanism | Question answered |
|---|---|
| MAC | Was this message authenticated by a holder of the shared secret, and has its authenticated content remained unchanged? |
| Cryptographic hash | Does this data produce the expected digest? |
| Digital signature | Does the signature verify under the corresponding public key? |
| Access-control policy | Is this participant permitted to perform the operation? |
| Replay protection | Has this operation already been processed? |
| Blockchain hash linking | Are the stored blocks consistent with their previous-hash references? |
| Consensus | Have participating network nodes agreed on the accepted state? |

These distinctions determine where MACs belong in a secure blockchain architecture and why HMAC authentication, digital signatures, cryptographic hashing, and distributed consensus must not be treated as interchangeable mechanisms.
