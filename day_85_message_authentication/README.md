# Message Authentication: Cryptographic Integrity and Sender Verification

## 1. Introduction

Message authentication is a security mechanism used to establish that a received message was generated by an entity possessing an authorized secret and that the message has not been modified during transmission.

It is an important component of secure communication systems, financial transaction processing, API security, distributed applications, and inter-service communication.

A message authentication system addresses two primary security requirements:

- **Message integrity:** Detect unauthorized modification of message content.
- **Data-origin authentication:** Establish that the message was generated by an entity possessing the required authentication key.

Message authentication does not automatically provide confidentiality, non-repudiation, or protection against every replay attack.

The five implementations demonstrate cryptographic authentication, message validation, key lifecycle management, replay prevention, and operational controls using different engineering approaches.

## 2. Fundamental Concepts

### 2.1 Message integrity

Message integrity ensures that received content corresponds to the content authenticated by the sender.

Consider a payment request:

| Field | Original value |
|---|---|
| Sender | alice |
| Receiver | bob |
| Transaction | INR 5,000 |
| Message ID | MSG-001 |

An attacker modifies the transaction amount to INR 50,000.

A correctly implemented message authentication mechanism detects this modification because the authentication tag no longer matches the received message.

Integrity verification must cover every security-relevant field, not merely the payload.

### 2.2 Data-origin authentication

Data-origin authentication establishes that a message was authenticated using a key associated with an authorized sender.

In symmetric authentication, both communicating parties possess the same secret key.

The receiver verifies the message using that secret.

Successful verification establishes that the message was generated by an entity possessing the shared key, subject to the security of the key-management and identity-binding systems.

It does not independently establish which individual used the key.

### 2.3 Authentication versus encryption

Authentication and encryption solve different security problems.

| Security mechanism | Primary purpose |
|---|---|
| Encryption | Confidentiality |
| Message authentication | Integrity and data-origin authentication |
| Digital signature | Integrity and public-key-based origin verification |
| Hash function | Message fingerprint generation |
| Authenticated encryption | Confidentiality and integrity together |

Encryption alone does not necessarily provide message authentication.

Similarly, an ordinary cryptographic hash does not authenticate the sender because anyone can calculate a hash of modified content.

## 3. HMAC: Hash-Based Message Authentication Code

### 3.1 Definition

HMAC is a message authentication construction that combines a cryptographic hash function with a secret key.

HMAC-SHA256 uses SHA-256 as its underlying hash function.

Its construction is:

\[
HMAC(K,m)=
H((K'\oplus opad)\parallel
H((K'\oplus ipad)\parallel m))
\]

Where:

- \(K\): Secret authentication key.
- \(m\): Message.
- \(H\): Cryptographic hash function.
- \(K'\): Key normalized to the hash block size.
- \(ipad\): Inner padding.
- \(opad\): Outer padding.
- \(\parallel\): Concatenation.
- \(\oplus\): Bitwise XOR.

For SHA-256:

| Parameter | Value |
|---|---:|
| Hash output | 256 bits |
| Digest length | 32 bytes |
| HMAC block size | 512 bits |
| Block length | 64 bytes |
| Recommended minimum key length in these implementations | 256 bits |

HMAC internally normalizes keys according to the underlying hash function's block size. The minimum key-length restriction is an application policy implemented by these examples.

### 3.2 Why HMAC is preferable to a keyed ordinary hash

A construction such as `SHA256(secret || message)` is not a suitable general replacement for HMAC.

HMAC uses a defined inner and outer hashing construction designed to provide message authentication while avoiding weaknesses associated with naive keyed-hash constructions.

### 3.3 SHA-256

SHA-256 belongs to the SHA-2 family.

Its processing mechanism includes:

1. Message padding.
2. Division into 512-bit blocks.
3. Message schedule expansion.
4. Compression rounds.
5. Final 256-bit digest generation.

The C++ implementation includes a complete SHA-256 implementation and uses it to calculate HMAC-SHA256 without external cryptographic libraries.

The Java implementation delegates cryptographic operations to the Java Cryptography Architecture.

Python uses `hashlib` and `hmac`.

JavaScript uses Node.js `crypto`.

PostgreSQL uses `pgcrypto`.

## 4. Message Authentication Workflow

A secure message-processing workflow separates message creation, authentication verification, replay detection, and business processing.

### 4.1 Message creation

The sender prepares a message containing:

- Sender identity.
- Receiver identity.
- Message identifier.
- Timestamp.
- Payload.
- Key identifier.

The sender serializes these fields into a deterministic byte representation.

The HMAC engine calculates the authentication tag using the sender's secret key.

The resulting message contains both the original content and the authentication tag.

### 4.2 Message transmission

The message is transmitted through an appropriate communication channel.

The transport mechanism may be HTTP, a message broker, a queue, or another communication protocol.

Transport security and message authentication provide complementary protections.

TLS protects a communication channel. HMAC can provide authentication and integrity at the message level, including when messages pass through intermediate systems.

### 4.3 Message verification

The receiver performs the following operations:

1. Validate message structure.
2. Validate field lengths and data types.
3. Check timestamp freshness.
4. Identify the authentication key.
5. Verify key ownership and status.
6. Recalculate HMAC-SHA256.
7. Compare the supplied and calculated authentication tags.
8. Register the message identifier for replay prevention.
9. Authorize subsequent application processing.

Business processing must not occur before successful authentication.

### 4.4 Authentication state machine

The implementations distinguish the following outcomes:

| State | Meaning |
|---|---|
| `AUTHENTICATED` | Message integrity and key ownership checks passed |
| `INVALID_SIGNATURE` | Authentication tag is incorrect |
| `UNKNOWN_KEY` | Key identifier does not exist |
| `REVOKED_KEY` | Key is no longer authorized |
| `EXPIRED_MESSAGE` | Timestamp is outside the permitted window |
| `REPLAY_DETECTED` | Message identifier has already been processed |
| `INVALID_MESSAGE` | Message structure or validation failed |

These outcomes are operationally different. Treating every failure as an invalid signature would make monitoring and troubleshooting less effective.

## 5. Canonical Message Serialization

### 5.1 Why serialization matters

Cryptographic algorithms operate on bytes rather than abstract application objects.

Two systems can represent the same logical message differently.

For example:

- Different JSON property ordering.
- Different whitespace.
- Different character encodings.
- Different timestamp formats.
- Different numeric representations.

If the sender and receiver serialize the same logical message differently, their HMAC calculations will differ.

Canonical serialization establishes one deterministic representation.

### 5.2 Implemented serialization approaches

| Implementation | Serialization strategy |
|---|---|
| Python | Sorted JSON keys and compact separators |
| JavaScript | Fixed object property ordering |
| C++17 | Length-prefixed fields |
| Java 17 | Length-prefixed fields |
| PostgreSQL | Canonical JSONB representation with normalized UTC timestamps |

The sender and receiver must use exactly the same serialization rules.

Canonicalization must also account for character encoding, timestamp precision, Unicode handling, and numeric representation.

A production protocol should specify these rules independently of individual programming languages.

## 6. Replay Attack Prevention

### 6.1 Definition

A replay attack occurs when an attacker captures a previously valid authenticated message and retransmits it.

The message may have a valid HMAC because its content and authentication tag have not changed.

Consequently, HMAC verification alone does not prevent replay attacks.

### 6.2 Message identifiers

Each message receives a unique identifier.

The receiver maintains a registry of previously accepted identifiers.

The effective replay identifier is:

\[
R=(SenderID,MessageID)
\]

When an authenticated message arrives:

- An unseen identifier can be registered.
- An existing identifier is rejected.
- Expired registry entries can be removed according to the retention policy.

### 6.3 Timestamp validation

The implementations use an allowed clock-skew interval.

A message is accepted only when:

\[
|T_{current}-T_{message}|\leq \Delta
\]

Where:

- \(T_{current}\): Receiver's current time.
- \(T_{message}\): Sender's message timestamp.
- \(\Delta\): Permitted clock difference.

Timestamp validation limits the useful lifetime of captured messages.

It does not replace unique message identifiers.

### 6.4 Distributed replay protection

An in-memory dictionary, Java concurrent map, or C++ set provides replay protection within a single running process.

Such mechanisms are insufficient when several application instances process the same messages.

Production systems require shared, atomic replay registration using an appropriate distributed store or transactional database.

The PostgreSQL implementation uses a composite primary key on sender and message identifiers to enforce uniqueness at the database level.

Replay retention must be at least as long as the period during which a message could legitimately be accepted.

## 7. Key Management

### 7.1 Key generation

Authentication security depends heavily on secret-key quality.

Keys should be generated using cryptographically secure random number generators.

The implementations use:

| Language | Key-generation mechanism |
|---|---|
| Python | `secrets.token_bytes()` |
| JavaScript | `crypto.randomBytes()` |
| C++17 | Deterministic demonstration generator |
| Java 17 | `SecureRandom` |
| PostgreSQL | `gen_random_bytes()` |

The C++ implementation deliberately uses a deterministic generator to keep the example self-contained. It is not suitable for production authentication keys.

### 7.2 Key ownership

Each key is associated with an authorized principal.

The authentication service checks whether the sender identity matches the key owner.

This prevents one registered principal from using another principal's key through the application's normal signing interface.

The key-to-identity mapping must itself be protected against unauthorized modification.

### 7.3 Key rotation

Key rotation replaces an existing authentication key with a new key.

The process involves:

1. Identifying the existing active key.
2. Generating replacement key material.
3. Registering the replacement.
4. Transitioning the old key to an inactive state.
5. Updating authorized signing systems.
6. Monitoring verification failures during migration.

The examples implement immediate revocation of the previous key.

Real deployments may require an overlapping transition period to support in-flight messages.

### 7.4 Key revocation

Revocation prevents further authentication using a compromised or unauthorized key.

Typical revocation causes include:

- Suspected key exposure.
- Employee or service-account termination.
- Unauthorized access.
- Cryptographic policy changes.
- Replacement during scheduled rotation.

Revocation status must be checked during verification, not merely during message creation.

### 7.5 Production key storage

The examples maintain keys in memory or demonstration database tables.

Production systems should use protected key-management infrastructure, strict access controls, secure secret distribution, auditing, and separation of administrative privileges.

Raw secret keys should never appear in application logs.

### 8.3 C++17 implementation

## 9. Authentication Versus Digital Signatures

HMAC and digital signatures both provide mechanisms for authenticating data, but their trust models differ.

| Property | HMAC-SHA256 | Digital signatures |
|---|---|---|
| Cryptographic model | Symmetric | Asymmetric |
| Secret material | Shared secret | Private signing key |
| Verification material | Same shared secret | Public verification key |
| Verification by third parties | Requires sharing the secret | Possible using the public key |
| Non-repudiation | Not provided | Supported under appropriate legal and operational conditions |
| Computational cost | Generally lower | Generally higher |
| Key distribution | Requires secure shared-secret distribution | Requires public-key distribution and trust validation |

In a shared-secret system, every authorized verifier possessing the secret can also generate valid authentication tags.

Therefore, HMAC cannot independently establish non-repudiation between parties sharing the same key.

## 10. HMAC and Authenticated Encryption

HMAC-SHA256 provides authentication and integrity but does not encrypt the message.

An attacker who intercepts an authenticated message may still read its contents.

When confidentiality is required, a suitable authenticated-encryption construction can provide both confidentiality and integrity.

Examples include AES-GCM and ChaCha20-Poly1305.

Authenticated encryption uses nonces or initialization parameters that must satisfy the algorithm's uniqueness requirements.

HMAC may also be used alongside encryption in a carefully designed protocol, but combining cryptographic mechanisms requires correct key separation and protocol design.

## 11. Security Controls and Failure Handling

| Security risk | Implemented control | Production consideration |
|---|---|---|
| Payload modification | HMAC verification | Authenticate all relevant fields |
| Unauthorized sender | Key ownership validation | Protect identity-to-key registration |
| Signature manipulation | Constant-time comparison | Use established cryptographic libraries |
| Replay attacks | Unique identifiers | Use shared atomic storage |
| Expired messages | Timestamp validation | Synchronize system clocks |
| Compromised keys | Revocation and rotation | Integrate with protected key management |
| Oversized messages | Payload-size limits | Apply transport and request limits |
| Duplicate processing | Replay registry | Use transactional processing |
| Secret exposure | Restricted key access | Avoid plaintext secret logging |
| Database tampering | HMAC and payload-integrity checks | Restrict privileged database access |

### 11.1 Timing attacks

An ordinary string comparison may reveal information through differences in execution time.

The implementations use:

- Python: `hmac.compare_digest()`.
- JavaScript: `crypto.timingSafeEqual()`.
- Java: `MessageDigest.isEqual()`.

The C++ demonstration uses a fixed-length comparison loop. It should not be treated as a complete side-channel-resistant implementation.

### 11.2 Atomic verification

Authentication and replay registration must be coordinated.

If two concurrent requests verify the same message, both must not be permitted to process it.

A robust workflow is:

`Receive → Validate → Verify HMAC → Register Replay ID → Commit → Process`

The replay registration must be atomic.

Business processing may require an additional transactional outbox or idempotency mechanism when external systems are involved.

### 11.3 Error reporting

Authentication failures should produce structured operational records.

Useful fields include:

- Message identifier.
- Sender identifier.
- Key identifier.
- Failure category.
- Event timestamp.
- Processing component.

Raw secret keys, authentication credentials, and sensitive message payloads should not be written to operational logs.

The relational model follows this structure:

`Principals`

`    |`

`    +---- Authentication Keys`

`    |          |`

`    |          +---- Key Rotation and Revocation`

`    |`

`    +---- Authenticated Messages`

`                 |`

`                 +---- Replay Registry`

`                 |`

`                 +---- Authentication Audit`

`                 |`

`                 +---- Message Processing`

The model distinguishes the registered sender, authentication key, message content, cryptographic verification result, and final processing state.

These entities have separate responsibilities.

A message being stored does not mean it has been authenticated.

An authenticated message does not necessarily mean that downstream business processing has completed.

## 13. Database Transaction Semantics

PostgreSQL provides transactional protection for authentication state changes.

Important operations include:

- Inserting a message.
- Verifying its authentication tag.
- Registering its message identifier.
- Recording the authentication decision.
- Updating the processing state.

The replay registry uses a composite primary key:

`(sender_id, message_id)`

This prevents duplicate registrations for the same sender and message identifier.

The verification function uses row-level locking and transactional database operations.

The sample script also demonstrates savepoints, procedures, reporting views, and cleanup operations.

For production systems, access to key-management functions and sensitive tables must be restricted through database roles and explicit privileges.

## 14. Performance and Complexity

Let:

- \(n\): Message size in bytes.
- \(k\): Number of registered keys.
- \(r\): Number of replay entries.

| Operation | Typical complexity |
|---|---|
| HMAC-SHA256 generation | \(O(n)\) |
| HMAC-SHA256 verification | \(O(n)\) |
| SHA-256 processing | \(O(n)\) |
| Hash-map key lookup | Expected \(O(1)\) |
| Ordered-map key lookup | \(O(\log k)\) |
| Hash-set replay lookup | Expected \(O(1)\) |
| Tree-set replay lookup | \(O(\log r)\) |
| Replay cleanup | \(O(r)\) for full scans |

The Python implementation uses dictionaries for key and replay storage.

The JavaScript implementation uses `Map`.

The C++ implementation uses `std::map` and `std::set`.

The Java implementation uses `ConcurrentHashMap`.

PostgreSQL uses indexed relational lookups and uniqueness constraints.

### Performance considerations

- Avoid repeated serialization of the same message.
- Enforce payload-size limits before expensive operations.
- Remove expired replay entries periodically.
- Avoid storing unlimited authentication history in memory.
- Use appropriate database indexes.
- Monitor key lookup and authentication latency.
- Use shared storage for horizontally scaled deployments.
- Apply request-rate limits before expensive processing.

## 17. Implementation Limitations

The implementations are educational reference systems rather than complete production security infrastructures.

Important limitations include:

1. **C++ key generation:** The demonstration generator is deterministic and must be replaced with a cryptographically secure source.

2. **In-memory state:** Python, JavaScript, C++, and Java examples use process-local registries. Distributed deployments require shared key and replay state.

3. **Database secrets:** The PostgreSQL example stores key material in a database column. Production deployments should use protected key-management infrastructure.

4. **Canonicalization:** The examples use different serialization approaches. Their generated signatures are not interoperable with one another without a shared serialization specification.

5. **Clock synchronization:** Timestamp-based freshness checks assume sufficiently synchronized clocks.

6. **Key rotation:** The examples implement simplified immediate revocation. Operational deployments may need controlled overlap between old and new keys.

7. **C++ cryptographic hardening:** The handwritten SHA-256 and HMAC implementation demonstrates algorithm mechanics but lacks the full validation, hardening, and assurance expected from established cryptographic libraries.

8. **Non-repudiation:** HMAC does not provide independent third-party proof of message origin.

9. **Confidentiality:** None of the HMAC implementations encrypts the message payload.

10. **Business transaction idempotency:** Replay protection prevents duplicate authenticated message acceptance, but external side effects require their own idempotency controls.

## 18. Technical Distinctions

The central security distinction is between authenticating a message and processing its contents.

A successful HMAC verification establishes that the message matches the authentication tag generated using the associated secret key.

Replay protection establishes that the message identifier has not already been accepted within the configured retention period.

Timestamp validation restricts message freshness.

Key management establishes whether the signing identity remains authorized.

Business processing determines what the application does with an authenticated message.

These are related but separate security responsibilities.

A reliable message authentication system must coordinate all of them without treating cryptographic verification as a substitute for identity management, confidentiality, authorization, or transactional integrity.
